react-indexeddb · Build Plan

A self-contained engineering reference. Open this file offline whenever you need to debug a regression, extend the library, or onboard yourself again in six months.

What this library is. A zero-runtime-dependency, TypeScript-first React hooks library that wraps IndexedDB and exposes it reactively. Same-tab and cross-tab. Works on React 16.8 - 19. Ships in 2.4 KB gzip.

What this document is. The "why and how" behind every file. The reactivity model, the transaction-safety contract, the error mapping, the test strategy, the recipes for adding features, and the playbook for the bugs you will hit when you change something.

How to use this doc Reading top-to-bottom takes about 25 minutes. If you are just here to debug, jump to §15 Debugging playbook and skim back from there. If you want to add a feature, start at §14 Extending.

2. Goals & non-goals

Goals (v1)

  • Reactive across components. A mutation in one component re-renders every subscribed component.
  • Reactive across tabs. A mutation in one browser tab re-renders subscribed components in every other tab on the same origin.
  • Schema-typed. One interface drives store names, key types, value types, and index names through every hook.
  • Zero runtime dependencies. The useSyncExternalStore shim is vendored, not depended on.
  • React 16.8 through 19. Native useSyncExternalStore on 18+, vendored shim on 16/17.
  • Concurrent-mode safe on React 18/19. Best-effort on 16/17.
  • SSR-safe. Lazy connection open. getServerSnapshot on every hook.
  • Small & readable. Seven files. Strict separation of concerns. ~2.5 KB gzip.

Non-goals (deferred or out of scope)

  • Atom-style API. Add later if a real user need appears.
  • Public db.transaction(...) escape hatch. Internal-only for now.
  • Storage-event cross-tab fallback. BroadcastChannel covers our matrix.
  • Microtask write-coalescing. Premature optimization without profiling.
  • TanStack-Query persistence adapter. Separate package if pursued.
  • Bulk methods (bulkPut, etc.) and cursor APIs. Deferred to v1.x.
  • Encryption / sync-to-server.
  • React Native. Hooks return "unsupported" at runtime.

3.3 Separation rules (the maintainability contract)

These are enforced by code review, not ESLint. Breaking them is the most common way to bake regressions into a future feature.

  1. db.ts is the only file that imports the indexedDB global.
  2. hooks.ts is the only file that imports React or shim.ts.
  3. store.ts imports neither React nor IndexedDB. It is pure JavaScript with a Map and a Set.
  4. crossTab.ts imports neither React, IndexedDB, nor store.ts. It only knows about BroadcastChannel.
  5. index.ts contains zero logic. Only re-exports.
  6. The INTERNAL symbol is the single contract between db.ts and hooks.ts. Never expose it from index.ts.

4. Module deep dive

Each layer in §3.1 is one source file. Here is what each one owns, what it must never do, and the patterns to know when you change it.

4.1 src/types.ts

type-onlyno runtime

The vocabulary of the library. Generic helpers that turn a user-declared schema interface into store names, key types, value types, and index name unions.

Public symbols

  • StoreSchema, Schema, SchemaLike<S>
  • StoreName<S>, KeyOf<S, N>, ValueOf<S, N>, IndexNameOf<S, N>, IndexKeyOf<S, N, I>
  • Database<S>, DatabaseQueryAPI<S>, DatabaseInternal<S>
  • MutationOp<S, N>, ConnectionStatus, QueryStatus, MutationStatus
  • INTERNAL symbol (the only runtime export, used as an object key)

Why SchemaLike<S> exists

TypeScript does not give an interface an implicit index signature, so a user's interface AppSchema { todos: ... } does not satisfy Record<string, StoreSchema> at the call site. SchemaLike<S> = { [K in keyof S]: StoreSchema } is an F-bounded constraint that lets a literal object type pass while still demanding StoreSchema-shaped values. Use it on every public generic.

Pitfalls

  • If you tighten a helper from S to S extends Schema, every test that uses an interface AppSchema {} will fail to compile. Use SchemaLike<S> at public entry points only; helpers should accept bare S with conditional fallback (S[N] extends { value: infer V } ? V : never).

4.2 src/shim.ts

~30 LOCMIT-attributed

Single export: useSyncExternalStore. On React 18+, re-exported from react. On 16/17, a tiny useState + useEffect fallback.

const NATIVE = (React as { useSyncExternalStore?: ... }).useSyncExternalStore;
export const useSyncExternalStore = NATIVE ?? useSyncExternalStoreFallback;

Why vendor it

The plan disallows runtime dependencies. The official use-sync-external-store/shim package is also MIT, ~30 lines, identical in behaviour for our use case (stable snapshots from store.ts). Vendoring is correct and is what most "zero-dep" libraries do.

Tearing caveat

Full concurrent-rendering tearing safety on R16/17 is impossible without React internals. The fallback is correct for stable snapshots but legacy roots have weaker guarantees than R18+ concurrent roots. The README documents this.

4.3 src/store.ts

framework-agnosticno Reactno IDB

The reactivity layer. Two maps: a per-channel version counter, and a per-channel listener set.

interface ReactivityStore {
  subscribe(channels: ReadonlyArray<string>, listener: () => void): () => void;
  getVersion(channels: ReadonlyArray<string>): number;
  notify(channels: ReadonlyArray<string>): void;
}

Snapshot stability rule

getVersion returns a sum of per-channel counters. Identical numeric values are Object.is-equal so React skips the render. notify increments the counter before firing listeners; the listener calls useSyncExternalStore's onStoreChange, which then re-reads getVersion, sees a new number, and re-renders.

Listener safety

A throwing listener does not break siblings. Each listener fires at most once per notify call even if it subscribed to multiple of the listed channels (deduplicated via a Set).

4.4 src/crossTab.ts

no Reactno IDBno store.ts

Wraps BroadcastChannel with a feature-detect and returns a uniform { post, onMessage, close }. The channel name is "react-indexeddb:" + dbName.

No-op fallback

If typeof BroadcastChannel === "undefined" we return a no-op channel. Hooks still work; cross-tab silently disables. We do not polyfill via storage events for v1.

Why no echo-to-self

The wire only fires the receivers (the sender does not get its own message back) so the same-tab store.notify does not double-fire. db.ts calls reactivity.notify locally and posts on the channel separately.

4.5 src/db.ts

only file importing indexedDB

The orchestrator. defineIDB(config) is the single public entry point.

Singleton open promise (StrictMode safe)

A module-level Map keyed by ${name}@${version} caches the Database<S> instance. A second defineIDB with the same key returns the same instance. onupgradeneeded runs at most once per page.

Single-request transactions

Every read and write op opens its own one-shot tx. readOne, readIndex, and writeOne all schedule one IDBRequest synchronously and return a Promise wired to request.onsuccess (reads) or tx.oncomplete (writes). We never await a foreign promise inside an open transaction. See §7.

Error capture pattern

Many browsers and fake-indexeddb leave tx.error as null when tx.onerror fires; the error is on the request. We capture request.onerror into a closure and use it from tx.onerror/tx.onabort:

let captured: Error | null = null;
const request = fn(tx.objectStore(storeName));
request.onerror = () => { captured = mapError(request.error); };
tx.oncomplete = () => resolve();
tx.onerror   = () => reject(captured ?? mapError(tx.error));
tx.onabort   = () => reject(captured ?? mapError(tx.error));

Mutation fan-out

mutate awaits the tx commit, then calls reactivity.notify([storeName]) and (if not opted out) channel.post({ stores: [storeName] }). The order matters: same-tab listeners fire before cross-tab so a fast in-process consumer never sees stale data.

Test-only escape hatches

__resetCache closes every cached connection and clears the cache. __dropCache clears the cache without closing - used by the cross-tab integration test to simulate two tabs in one process.

4.6 src/hooks.ts

only file importing React

Three hooks, ~30-60 LOC each. None of them imports the IndexedDB global directly; they go through db[INTERNAL].

useIDB(db)

Subscribes to a special status channel. Calls internal.getConnection() in an effect on mount so the open is lazy. SSR snapshot returns { status: "loading" }. The status object reference is memoized: identical { status, error } reuses the previous reference.

useIDBQuery(db, fn, stores)

The single read hook. Subscribes to the union of stores; useSyncExternalStore returns a numeric version. An effect with deps [db, version] re-runs the user's fn when either changes. The user's fn is held in a ref so re-renders without an invalidation do not re-fire it.

stores is content-stabilized via storesKey = stores.join("\u0000") + useMemo so passing a fresh array literal each render does not cause re-subscribes.

useIDBMutation(db, store)

State machine: idle → pending → success | error. mutate calls internal.mutate and rethrows. A mounted ref prevents setState after unmount.

4.7 src/index.ts

pure barrel

Only re-exports from db.ts, hooks.ts, and types.ts. Never re-exports the INTERNAL symbol. If you ever feel the urge to put a function in index.ts, put it in the appropriate layer and re-export it instead.

5. Reactivity walkthrough

Putting the layers together: what happens between a user clicking a button and another component re-rendering.

The lifecycle of a write + reactive read

  1. Component A calls mutation.mutate({ type: "put", value }).
  2. useIDBMutation sets state to pending, then awaits internal.mutate("todos", op).
  3. db.ts.mutate calls writeOne("todos", s => s.put(value)).
  4. writeOne opens a fresh readwrite transaction on "todos", schedules the put, and returns a Promise wired to tx.oncomplete.
  5. The browser's IDB engine commits the transaction. tx.oncomplete fires; the Promise resolves.
  6. Back in db.ts.mutate, control resumes after await writeOne(...). We now call reactivity.notify(["todos"]) followed by channel.post({ stores: ["todos"] }).
  7. store.ts.notify bumps the per-channel version counter for "todos" and calls every listener subscribed to it (deduplicated).
  8. Component B's useIDBQuery(db, fn, ["todos"]) subscribed via useSyncExternalStore. Its onStoreChange fires, React re-reads getSnapshot, the new numeric version differs by Object.is, React schedules a re-render.
  9. The render reads version from useSyncExternalStore, which is in the deps of an effect that runs fn(db) again. The Promise resolves with the new data and the component sees the updated value.
  10. Component A's mutation hook flips its state to success. The mutation Promise resolves.
Order of operations (same tab vs cross-tab) We notify locally first, then post on the channel. Other tabs receive the message via BroadcastChannel.onmessage and call reactivity.notify in their own process. Each tab has its own ReactivityStore instance because defineIDB in tab 2 creates one when its module loads.

Why the version-counter snapshot

useSyncExternalStore's contract: getSnapshot must return the same value (by Object.is) until something changes. If the snapshot is a fresh object each call, React assumes the store changed and infinite-renders.

We use a number per channel and sum them for the dep list. Numbers are Object.is-stable, identical sums compare equal, and any notify on a relevant channel strictly increases the sum.

Why an effect, not useSyncExternalStore alone, for the user's fn

The user's fn is async (it queries IDB). useSyncExternalStore requires synchronous snapshots. So we use useSyncExternalStore just for the version, then drive a regular useEffect with [db, version] deps to await the user's Promise and store the result in useState.

6. Cross-tab flow

Cross-tab uses BroadcastChannel. Each tab owns its own Database<S> object, its own ReactivityStore, and its own BroadcastChannel instance bound to the channel name "react-indexeddb:" + dbName.

sequenceDiagram
  participant TabA
  participant ChanA as BroadcastChannel A
  participant Bus as Browser bus
  participant ChanB as BroadcastChannel B
  participant TabB
  TabA->>ChanA: post({ stores: ["todos"] })
  ChanA->>Bus: postMessage
  Bus->>ChanB: onmessage
  ChanB->>TabB: emit message
  TabB->>TabB: reactivity.notify(["todos"])
  TabB-->>TabB: useIDBQuery re-runs fn(db)

What is in the message

interface CrossTabMessage {
  stores: ReadonlyArray<string>;
}

That is the entire wire format. We do not ship payloads; receivers re-read from IDB. This keeps the protocol forward-compatible: adding more stores, indexes, or even data shapes never changes the wire.

Why not echo to self

BroadcastChannel by spec does not deliver to the sender, but our test fake mirrors that. Echo-to-self would cause every mutation to invalidate twice in the source tab.

Disabling cross-tab

Pass { crossTab: false } to defineIDB. We swap the real channel for a no-op (and skip onMessage wiring). Useful for tests, embedded WebViews, or when an app explicitly does not want it.

7. Transaction contract

This is the one rule that, if broken, will create real data corruption. Memorize it.

Never await a foreign Promise inside an open IDBTransaction. The browser auto-commits an IDB transaction when its task queue empties. awaiting anything that does not directly settle on an IDBRequest yields control to the macrotask queue, the IDB engine sees no more pending requests, and the transaction commits early. Subsequent operations on it will throw InvalidStateError.

How db.ts respects the contract

  • Every read and write op opens its own tx and waits on a single request.
  • The user never gets a raw IDBTransaction handle.
  • useIDBMutation.mutate is one tx per call.
  • useIDBQuery.fn can call multiple db.get/db.getAll operations - each runs in its own tx so awaits between them are safe.

What this means for performance

One tx per op is more transactions than a hand-rolled batch. For typical UI workloads (single-record reads/writes per render) the cost is negligible. If you ever need bulk semantics in a single tx (atomicity), add a v1.x db.transaction(stores, mode, syncFn) escape hatch where syncFn is required to be synchronous and the library awaits tx.done for you.

What changes if you add features

Anything that takes a callback intended to schedule IDB requests must require the callback to be sync, or accept a Promise that only ever resolves from request-success handlers wired before yielding. The README and dev-build console warnings are how we keep users from violating this themselves.

8. Error mapping

Every recoverable IDB error is mapped to a typed class so application code can instanceof-discriminate.

ClassTriggered byRecovery
IDBVersionErrorOpen with a lower version than already on disk; corrupted version fieldBump version in code and reload, or call indexedDB.deleteDatabase as a last resort
IDBBlockedErrorAnother tab holds a connection on an older version, blocking your upgradeAsk the user to close other tabs; listen for onversionchange in the blocking tab to auto-close
IDBQuotaExceededErrorBrowser storage limit reached during a writePrune old records, ask the user to clear cache, drop optional caches
IDBUnsupportedErrorindexedDB not available (SSR, RN, Firefox private browsing, Safari private fail)Render a degraded experience or surface a "feature unavailable" UI

Where the mapping happens

db.ts.mapError(err) is the single conversion point. It inspects err.name from a DOMException and returns the matching typed Error. Every reject in db.ts goes through it.

Adding a new error class

  1. Declare the class in db.ts next to the others.
  2. Map its DOMException.name in mapError.
  3. Re-export from index.ts.
  4. Add a row to the table in the README.
  5. Add a test that triggers the underlying DOMException via fake-indexeddb if possible.

9. SSR & StrictMode

SSR

  • defineIDB never opens IDB at import time. The connection lazily opens when something calls internal.getConnection() - that is, when useIDB mounts on the client.
  • useIDB's getServerSnapshot returns { status: "loading" }. useIDBQuery's server snapshot is 0 (the version), and the data state defaults to { data: undefined, status: "loading" }.
  • For Next.js App Router, mark client files with "use client". Never call defineIDB from a server component.
  • Hydration mismatches happen when the client side renders different markup based on data that was undefined on the server. Always gate UI on status === "success" or render a skeleton.

StrictMode

  • React 18+ StrictMode mounts effects twice. The singleton open-promise cache makes the second mount a no-op (returns the same Database instance).
  • The useIDBMutation mounted ref correctly resets on the second mount.
  • The useIDBQuery effect's cancellation (let cancelled = false; ... return () => { cancelled = true; }) means the first mount's in-flight Promise becomes a no-op when the second mount supersedes it.

How the shim is selected

shim.ts reads (React as any).useSyncExternalStore at module init. If present (R18+), the named export is the native function; otherwise, it is the fallback. The bundler keeps both code paths but tree-shakers can drop the fallback if a downstream app provides a side-effect-free react module - in practice both ship.

Pitfalls when bumping React

  • If React 20+ ever changes useSyncExternalStore's signature, our shim's fallback signature is the canonical source of truth - keep it backward compatible.
  • If React eventually formalizes a "transition" API for selectors, consider an opt-in { priority: "transition" } for useIDBQuery.

11. Test strategy

Tooling

  • Vitest + jsdom: unit and component tests.
  • fake-indexeddb: drop-in IDB polyfill auto-loaded in test/setup.ts.
  • @testing-library/react: component rendering and queries.
  • tsc --noEmit against test-d/: type-level assertions via expectType and @ts-expect-error.
  • esbuild + zlib gzip: bundle-size guard in scripts/size.mjs.

Test layout

Coverage gates

vitest.config.ts sets thresholds: 85% lines/functions/statements, 80% branches. src/index.ts and src/types.ts are excluded - they are pure re-exports / types.

Patterns to copy

  • Use uniqueDbName() (in test/helpers.ts) for every test to avoid cross-test contamination, even with fake-indexeddb.
  • Use __resetCache() in afterEach to close every connection. __dropCache() only when intentionally simulating two tabs.
  • For mutation error paths, capture the rejection via act(() => mutate(...).catch(setLastError)) or by waiting on status === "error" with waitFor.

What is intentionally not tested

  • Real-browser cross-tab. Requires Playwright + multi-context. Optional CI job, not a hard gate.
  • Real-browser quota errors. Mocked via fake-indexeddb only; real quota behaviour is browser-specific.

12. Build & publish pipeline

tsup

Single entry src/index.ts, dual output ESM (.js) and CJS (.cjs) plus .d.ts/.d.cts. react and react-dom externalized. treeshake: true. Output goes to dist/.

Size guard

npm run size reads dist/index.js, re-bundles with esbuild minified, gzips, and exits non-zero if > 5 KB. Currently we are around 2.4 KB gzip; CI fails the build the moment we cross the budget so a regression is caught before merge.

Publish

prepublishOnly chains build + test + test:types. publishConfig.access = "public". The files array publishes only dist/, README.md, LICENSE (and implicitly package.json).

Versioning

  • Patch: bug fixes, perf, internal refactors, doc-only changes.
  • Minor: new hooks, new error classes, new optional config flags.
  • Major: API removals, generic-shape changes, dropping a React major.

Always pre-tag with npm version --no-git-tag-version from a clean tree, push, and let CI verify before publishing.

13. CI matrix

.github/workflows/ci.yml defines three jobs:

  • build: matrix of Node {18, 20, 22} × React {16.14, 17.0.2, 18.3.1, 19.0.0}. Installs the React peer dynamically, runs build + test + test:types.
  • lint: single Node 20 job, runs npm run lint.
  • size: builds once and runs npm run size. Hard gate.

When a matrix cell fails

  • R16/17 only: very likely a shim regression. Check shim.ts and the useIDBQuery effect deps.
  • R19 only: a future React internals change. File an issue; native useSyncExternalStore rarely changes.
  • All matrices: a real bug; reproduce locally with npm test first.

14. Extending the library

Recipes for the most likely v1.x features. Each one calls out which layers change and which tests to add.

Recipe A: add a new query method (e.g. byKeyRange)

  1. types.ts: extend DatabaseQueryAPI<S> with the new signature.
  2. db.ts: implement on the queryApi object using readOne/readIndex primitives. New tx per call. Map errors via mapError.
  3. hooks.ts: usually no change - users call the new method from inside useIDBQuery's fn.
  4. tests: add a db.test.ts case for happy path and one for an invalid range. Add a test-d/ assertion that the return type is correct.
  5. README: one row in the API table.

Recipe B: add a new error class

See §8. Two-line code change in db.ts + one-line export in index.ts + table row.

Recipe C: add a public db.transaction(stores, mode, syncFn) escape hatch

  1. types.ts: add to DatabaseQueryAPI with a constraint that syncFn's return is T | Promise<T> but the doc requires sync-only IDB calls.
  2. db.ts: open one tx, pass the IDBObjectStore(s) to syncFn, await tx.oncomplete, return the user's value. Stamp reactivity.notify(stores) + channel.post on success.
  3. tests: include the "user awaited a foreign promise" anti-pattern and verify the error is recognizable.
  4. README: prominent warning. This is the one place users can shoot themselves in the foot.

Recipe D: add bulk methods (bulkPut, bulkDelete)

  1. types.ts: extend MutationOp<S, N> with new variants { type: "bulkPut", values: ValueOf<S, N>[] } etc.
  2. db.ts: handle in writeOne's callback by issuing multiple store.put(v) calls inside a single tx synchronously - the engine batches them.
  3. tests: hooks test for useIDBMutation handling the new op.

Recipe E: support cursor-based queries

Cursors are stateful and span multiple events. Wrap them in a generator-style helper that returns an array (terminating the cursor when filtered) - do not expose raw cursors. Keep transaction lifetime equal to the cursor's onsuccess chain.

Recipe F: TanStack Query persistence adapter

Different package (@react-indexeddb/persister-query). Reuses defineIDB + useIDBMutation. Out of scope for this repo.

Recipe G: storage events fallback for cross-tab

Skip unless a real user reports broken cross-tab on a target browser. The implementation lives entirely in crossTab.ts; no other layer needs to know.

15. Debugging playbook

The bugs you will actually hit, and the first place to look.

Symptom: a component does not re-render after a mutation

  1. Confirm the stores array passed to useIDBQuery includes the store you mutated. Otherwise, no listener was registered.
  2. Look at useIDBQuery's storesKey - if you pass a fresh array each render whose joined key changes, the subscribe-unsubscribe cycle can drop the bump. (Should not happen given the useMemo; but a custom wrapper hook could break it.)
  3. Check whether the user's fn closes over stale state. The Promise resolves to the value read by the new tx, but if the user transforms it via captured props, that capture is from the previous render.
  4. Verify reactivity.notify is being called from db.ts.mutate - log storeName.

Symptom: InvalidStateError: The transaction has finished

Almost certainly an await on something other than an IDBRequest inside an open tx. See §7. Move the await outside the tx, or refactor to one tx per op.

Symptom: cross-tab works in Chrome but not in Firefox / Safari

  1. Check typeof BroadcastChannel in DevTools. Safari supports it from 15.4. If undefined, our no-op fallback is engaged.
  2. Both tabs must be on the same origin (scheme, host, port). Cross-origin iframes have separate channels.
  3. Private browsing in Safari historically blocks IDB writes - IDBUnsupportedError appears as a successful open followed by failing writes.

Symptom: onupgradeneeded runs every page load

You bumped version without adding store creation, so the upgrade callback runs and does nothing - but it still runs only when the version changed. If it runs every load, the user's upgrade callback might be opening a new transaction or doing async work, which it must not. Upgrades are sync - schedule store creation directly on the IDBVersionChangeEvent.target.result.

Symptom: bundle size CI fails

  1. Run npm run build && npm run size locally.
  2. Look at dist/index.js for surprising imports. Common offenders: a console.warn in production, a verbose error message, an inadvertent import * from "react".
  3. If a feature genuinely justifies the size, increase the budget intentionally in scripts/size.mjs. Do not silently raise.

Symptom: types pass tsc in src/ but fail in user code

Probably a SchemaLike<S> regression - see §4.1. Add the user's failing example to test-d/schema.test-d.ts.

Symptom: StrictMode double-invocation breaks something

  1. Confirm defineIDB's singleton cache is hit on the second mount (console.log the cache key).
  2. Hooks: each effect needs an idempotent body or a clean teardown.
  3. useIDBMutation.mutate is fine to fire twice; idempotency is the user's job (e.g. don't generate a fresh UUID inside mutate body).

17. Glossary

Channel
In store.ts, a string key (usually a store name, plus a few specials like __status__) that listeners subscribe to. Independent of BroadcastChannel.
External store
A data source outside React's render-tree. useSyncExternalStore is React's API for subscribing to one tearing-safely.
F-bounded polymorphism
A generic constraint that uses the type parameter on both sides, e.g. S extends SchemaLike<S>. Lets us accept user-defined interfaces without forcing index signatures on them.
Notify-then-broadcast
Our cross-tab order: invalidate locally first, post to other tabs second. Avoids racing same-tab listeners against the channel.
One-shot transaction
A transaction opened to schedule exactly one IDBRequest. Closes itself when that request settles. The unit of work in db.ts.
Snapshot stability
The contract that getSnapshot returns identical-by-Object.is values until something changes. Without it, useSyncExternalStore infinite-renders.
Tearing
When two components in the same render commit see different values from the same external source. useSyncExternalStore on R18+ guarantees no tearing.
Vendored shim
A small dependency copied into src/ rather than installed from npm. Our shim.ts is one.
